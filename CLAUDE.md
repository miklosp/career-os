# Career-Ops — Agent Rules

An AI job-search pipeline wired into Claude Code and custom dashboard. Human overview lives in `README.md`.

## Personalization

User-specific content (archetypes, narrative, proof points, location policy, comp anchor, voice) goes in `user/config/profile.md` — YAML frontmatter for the structured contracts (`candidate`, `location_policy`), markdown body for everything LLM modes read as prose. 

| Request | Edit |
|---|---|
| Archetypes / narrative / scoring bonuses (user) | `user/config/profile.md` |
| Add companies | `user/config/portals.yml` |
| Scoring defaults (weights, bands, archetype detection) | `modes/_eval.md` |
| Writing & ATS standards (CV, cover letter, form answers) | `modes/_writing.md` |
| CV template design | `style/cv-template.css` |
| Per-ATS form mechanics (Ashby, Greenhouse, Lever...) | `modes/_ats/{slug}.md` |
| Scan sources, incl. the rejected list | `modes/_scan-sources.md` |

## Data Contract (CRITICAL)

- **`user/`** — all user data, in its own private git repo, gitignored by this repo. Code resolves it only through `lib/paths.mjs` (Go: `dashboard/internal/paths`); `CAREER_OPS_USER_DIR` overrides the location. Never join the repo root with `config`/`data`/`output`/`transcripts`. Paths stored *inside* user data (tracker `[NUM](data/reports/…)` links, TSVs) are relative to `user/`, with no `user/` prefix. Secrets stay in the root `.env`, never in `user/`.
- **`user/config/`** — user-edited inputs. `cv.json`, `profile.md`, `portals.yml`, `story-bank.md`, `aliases.yml`, `notes.yml`, `cover-letters/` (accepted, candidate-edited letters; `modes/cover-letter.md` matches the newest). Personalization goes HERE.
- **`user/config/cv.json` is the canonical CV** (JSON Resume superset: per-bullet stable `id`s, `skills_inventory`, `evidence_refs`). `user/config/cv.md` is a *derived* human-readable view, regenerated by `lib/cv-json-to-md.mjs` (`pnpm cv-build`); never hand-edit it. `lib/cv-schema.mjs` is the single parser/serializer; `lib/cv-md-to-json.mjs` (`pnpm cv-migrate`) re-imports prose edits back to JSON.
- `user/config/story-bank.md` holds STAR+R stories (its `**ID:** S0xx` are valid `[src:]` targets). **NEVER hardcode metrics — cite from these at evaluation time.**
- **`user/transcripts/`** - interview transcripts, notes, email feedback
- **`user/data/` + `user/output/`** — system-written state
- **`user-template/`** — the starter `user/` layout with placeholder content; a new user copies it to `user/`. It holds example data only, never real user content.
- Everything else (`modes/`, `lib/`, `dashboard/`, `templates/`) is implementation, edited freely. **NEVER put user-specific content in system files.**

## The Pipeline

URLs are prepped by a **zero-token script in-session**, then scored by **batched background agents** (4 JDs per agent, `model: "sonnet"`, ≤ 3 concurrent). Full orchestration: `modes/auto-pipeline.md`.

1. **Prep** — `node lib/prep-jds.mjs <url...>` (deterministic, zero-token): per URL, `lib/fetch-jd.mjs` (dedup, ban list, NUM via `lib/next-num.mjs`, save `user/data/jds/{NUM}-*.md`, insert `Fetched` row) then `lib/location-gate.mjs`. Emits the eval queue as one JSON line. `unknown-host`/`error`/orphan URLs are deferred to **solo agents** — the only path that loads `modes/_fetch.md`, which teaches `lib/ats-registry.json` so the next hit is zero-token.
2. **Location gate** — deterministic rules run inside prep (`Skipped-Location` rows written by the script, quoted JD evidence in Notes). JDs flagged `needs-llm` are gated by the eval agent via `modes/_location-gate.md` vs `user/config/profile.md` `location_policy` before scoring; on SKIP, no report.
3. **Score** — `modes/_eval.md` in the batch agent: one `node lib/eval-context.mjs <num...>` call supplies the annotated CV, profile, story-bank digest, confirmed notes, report example, and every JD in a single turn; each JD is a **sealed, independent evaluation** (no cross-JD comparison or citation reuse). JD-text-only triage, **zero WebSearch**. A/B/C/D scored; weighted global score in the `**Score:**` header. Writes `user/data/reports/{NUM}-*.md` + a TSV in `user/data/tracker-additions/` per JD.
4. **CV personalization** — user-triggered only (dashboard `t` → interactive `tailor` session, or `/career-ops tailor`).

Agents NEVER call `merge-tracker.mjs` or `dedup-tracker.mjs` — only the user does.

## Skill Modes

| User intent | Mode |
|---|---|
| Pastes one or more URLs | `auto-pipeline` (prep script → batched bg eval agents) |
| Find new offers | `scan` (then feed `DISPATCH_URLS` into `auto-pipeline`) |
| Fill an application form | `apply` |
| Tailor a CV interactively before applying | `tailor` (criteria gaps → elicit evidence → session drafts the tagged CV → `lib/cv-draft.mjs finalize` → review walkthrough → PDF; hands off to apply) |
| Write a cover letter | `cover-letter` (one-page PDF + paste text; standalone or called by `apply`) |
| CV health / optimization walkthrough | `cv` (deterministic `lib/cv-status.mjs` + interactive next-action walk) |
| Interview prep for a company | `interview-prep` (web research allowed here) |
| Manage the story bank | `storybank` (`review` / `add` / `status`) |
| Drill answers against a rubric | `practice` |
| Full simulated interview + debrief | `mock` |
| Score a real-interview transcript | `analyze` |
| First-run setup (missing config) | `onboarding` (see below) |

CV/PDF generation runs through the `tailor` mode — dashboard `t` key or
`/career-ops tailor`. The interactive session itself drafts the CV; no
generator API call. See `README.md`.

Use path references to mode files, never inline their content into agent prompts — the agent reads only what it needs via Read.

## Onboarding

Silently each session, check: `user/config/cv.json`, `user/config/profile.md`, `user/config/portals.yml` exist and `cv.json` no longer carries the template name `Your Name`. If `user/` has no data yet, create it from the starter layout: `mkdir -p user && cp -R user-template/. user/` (see `user-template/README.md`).

**If any required file is missing or still a placeholder, enter onboarding — do nothing else until basics exist.** Follow the walkthrough in `modes/onboarding.md` (CV → profile → portals → tracker → deepen → confirm). Also reachable on demand via `/career-ops onboarding`.

**After every evaluation, learn.** Score-too-high / missed-experience feedback → update `user/config/profile.md`, never system-layer files.

## CV Generation → Fact-Check

Provenance-contracted pipeline: the interactive `tailor` session drafts the CV under the `[src: id]` citation contract in `lib/prompts/ats-prompt.md` → deterministic finalize + validator (`lib/cv-draft.mjs finalize` → `lib/cv-validate.mjs`) (`lib/cv-validate.mjs`) → two independent parallel reviewers in one script (`lib/cv-fact-check.mjs`): an ATS simulator (`REVIEW_MODEL`, same family as Ashby's evaluator) and a citation fact-checker (`FACTCHECK_MODEL`, a third model family). Validator and reviewers are **separate controls**; the reviewers never substitute for the validator. Agent-relevant rules:

- The session gets its inputs in one call, `node lib/cv-draft.mjs context {NUM}`: the contract with the **id-annotated** CV, confirmed `user/config/notes.yml`, story bank, the latest `user/data/reports/{NUM}-*.md`, and the JD filled in. It writes the draft to `user/output/customized-cvs/{NUM}-{slug}-cv-draft.md`. Closed-world evidence for any claim: `user/config/cv.json` bullet id · story-bank `S0xx` · confirmed note `n#` · Block-A Match id. Block-A Gaps are forbidden; raw JD only supplies wording for already-validated claims.
- Every output bullet ends exactly one `[src: id]` and is ≤25 words; the Summary (≤85 words) ends a composite `[src: …]`; Core Competencies is closed-world over `cv.json.skills_inventory ∪ user/config/aliases.yml`. The validator hard-fails missing/unknown ids, multi-id bullets, over-length bullets/summary, unsupported high-risk entities, out-of-inventory skills: finalize prints the `<failed_constraints>` block, exits non-zero, and writes nothing; the session fixes the draft in front of the user and reruns (no retry cap). On pass, `[src: id]` tags are stripped and everything except the Summary, the competency selection, and the bullets is projected: identity from `profile.md`; headline, role and sub-entry headings, dates, meta lines, descriptions, languages, and education from `cv.json` (a draft heading with no `cv.json` match fails).
- Per-generation audit: `user/output/customized-cvs/{NUM}-{slug}-trace.json` (bullet→src, `<gaps>`, `<bridges>` with `source_type`, validator chain). The fact-checker consumes this (citation map + gaps); the ATS simulator scores the CV text alone against the report's Criteria ledger (per-criterion meets/uncertain/does-not-meet; met/total and overclaim/uncertain/lost deviations computed in code). Both merge into one review JSON. Report-only — neither injects text.
- Severity tiers / default actions: `fabricated` (no support → conservative fix); `stretched` (thin → conservative downgrade); `bridge` (CV↔JD vocabulary substitution → **keep CV text**, upgrade only if the user genuinely has the JD-term experience).
- A row with `review-pending` status: pressing Enter opens the fact-check walkthrough **before** the report. Forced gate.
- Never auto-revise from reviewer output — cascading edits introduce new leaks. Reviewer surfaces; user applies.

## Ethical Use (CRITICAL)

Quality, not quantity. Genuine matches, not mass applications.

- **NEVER submit an application without the user reviewing first.** Fill forms, draft answers, generate PDFs — STOP before Submit/Send/Apply.
- Score < 4.0/5 → explicitly recommend against applying; proceed only on a stated user override.
- Every application costs a human's attention. Guide toward fewer, better applications.

## Offer Verification (MANDATORY)

**NEVER trust WebSearch/WebFetch to confirm an offer is still active.** Firecrawl first; ephemeral `agent-browser` only if Firecrawl 403s/empty.

```bash
set -a; source .env; set +a
firecrawl scrape "<url>" -o /tmp/verify.md
```

agent-browser fallback — ephemeral session, **mandatory close even on failure** (use `;`/trap; skipping it leaks Chromium):

```bash
agent-browser --session-name verify open "<url>" && agent-browser --session-name verify snapshot -i
agent-browser close --session-name verify
```

Classify: footer/navbar only = closed; title + description + Apply = active. Background `claude -p` agents without agent-browser: fall back to WebFetch and mark the report header `**Verification:** unconfirmed (background mode)`.

## Conventions & Pipeline Integrity

- Node `.mjs` scripts, YAML config, Markdown data, Go TUI dashboard. Sequential 3-digit NUM via `lib/next-num.mjs` only. Conventional commits.
- **After an evaluation batch lands in `user/data/tracker-additions/`: `node merge-tracker.mjs` THEN `node lib/dedup-tracker.mjs`** (that order — dedup needs merged state). User-only.
- **NEVER append a new applications.md row for a company+role that already exists.** `merge-tracker.mjs` promotes the `Fetched` row in place; new rows only when there is no match.
- `lib/scan-history.mjs` is the single shared writer for `user/data/scan-history.db` — every path records through it; no ad-hoc `INSERT INTO offers`. The DB is the authoritative dedupe index. Reconcile with `node lib/scan-history.mjs --backfill` (idempotent).
- **Ban list:** a URL/company matching an enabled `banned_companies` entry in `user/config/portals.yml` is dropped at the earliest zero-cost point of every path (`fetch-jd.mjs` Guards A/B, scan filters). `fetch-jd.mjs` emits `status:'banned'` → agents stop silently. Logged in `scan-history.db` as `banned`, never an applications.md row.
- Health: `node lib/verify-pipeline.mjs`. Normalize: `node lib/normalize-statuses.mjs`. Dedup: `node lib/dedup-tracker.mjs`.
- All mode files are English. Reports/CVs match the JD's language at generation time (EN default).

### Pipeline Integrity rules

1. Fetch agents MAY add `Fetched` rows directly — pipeline entry point.
2. Scoring agents NEVER append rows — they write a TSV; merge promotes the existing row in place.
3. You MAY edit applications.md to update status/notes of existing entries (e.g. `Evaluated` → `Applied`).
4. Every report header includes `**URL:**` (between `**ID:**` and `**Summary:**`). No `**PDF:**` line in reports — PDF status lives only in applications.md.
5. All statuses canonical (below; source of truth `templates/states.yml`).

### TSV for tracker additions

One file per evaluation: `user/data/tracker-additions/{num}-{company-slug}.tsv`, single line, 9 tab-separated columns **in this order (status BEFORE score)**:

```
{num}	{date}	{company}	{role}	{status}	{score}/5	{pdf ✅|❌}	[{num}](data/reports/{num}-{slug}-{date}.md)	{note}
```

In applications.md score comes before status; `merge-tracker.mjs` handles the swap.

### Tracker columns

`user/data/applications.md` has 13 columns: `# | Date | Company | Role | Score | Status | PDF | Report | Notes | Applied Date | Channel | Furthest Stage | Rejection Reason`. The last four are outcome fields, never in a TSV: `apply` sets Applied Date (YYYY-MM-DD) + Channel + Furthest Stage `none` when marking `Applied`; whoever records a later stage or rejection updates Furthest Stage / Rejection Reason in place. Furthest Stage only moves forward — a terminal status never clears it. Vocabularies (Channel `cold-ats|referral|recruiter|exec-search|outreach`, Furthest Stage `none|screen|assessment|hm|panel|final|offer`) live in `templates/states.yml` `outcome`. Pipes inside any cell become `/`.

### Canonical states

`Fetched` (JD saved, awaiting gate+score) · `Skipped-Location` (gate skip; Notes = `<rule-id>: "<evidence>"`) · `Evaluated` (report done) · `Applied` · `Responded` · `Interview` · `Offer` · `Rejected` · `Discarded` (candidate dropped / offer closed) · `SKIP` (manual don't-apply).

Status field: no `**bold**`, no dates (use date column), no extra text (use notes column).
